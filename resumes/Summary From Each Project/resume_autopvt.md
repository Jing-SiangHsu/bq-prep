# AutoPVT — Resume Content

**Role:** Full-Stack Engineer (primary backend + cross-stack architect on later features)
**Stack:** Go (gRPC services + grpc-gateway), Protocol Buffers (shared schema across 5 repos), PostgreSQL, Vue 3, WebSocket, TypeScript
**Scope:** 5 repos (autopvt-api, autopvt-db, autopvt-mgmt-ui, autopvt-type, autopvt-ui), 527 commits over ~1 year
**What it is:** An internal production-verification-test (PVT) platform — testers run structured test plans against physical network-switch hardware ("test boxes"), with a cloud backend coordinating multi-tester sessions, live progress, and report generation.

> Honest framing: none of this is an AI/ML pipeline. The reason it's relevant to an AI Engineer role is that the hardest problems here — keeping shared state consistent under concurrent writers, streaming live state changes to many clients, designing versioned schemas across services, and building auditable systems — are the exact same problems that show up in multi-agent orchestration, agent state stores, and tool/function-schema design. The bullets below describe the real work; the framing notes after each section connect it to that overlap.

---

## Resume Bullets

- Designed and shipped an **optimistic-concurrency-control system** for multi-user concurrent editing of shared test-execution state, combining PostgreSQL advisory locks (per-resource exclusive locks for structural writes, shared locks for concurrent field writes) with an atomic compare-and-bump revision check — eliminating silent overwrite/data-loss bugs when multiple testers worked the same test session simultaneously.
- Built a **real-time event broadcast layer** (gRPC server-streaming + WebSocket fan-out) that propagates every state-changing action to all connected clients with resolved actor identity and a human-readable change diff, powering live "who changed what" UI cues and a tamper-evident audit trail from a single shared code path.
- Designed and implemented a **Postgres LISTEN/NOTIFY → gRPC streaming pipeline** for live firmware-build events, explicitly scoping the delivery model to at-most-once/live-only (vs. backfill-on-reconnect) and documenting the tradeoff in a public spec; diagnosed and resolved a production service-registration gap during live integration testing with an external client team.
- Owned a **5-repo, protobuf-driven schema-evolution pipeline** (single source of truth in a shared `.proto` package, codegen to Go + TypeScript, submodule-pinned across 4 consumer services) — including a major data-model migration (integer IDs → external-system string IDs, enum restructuring) that required keeping a Firebase sync service, Postgres schema, gRPC API, and two frontends contractually aligned.
- Re-architected the test-data API around a **lazy-loading, versioned-fetch pattern**: stripped heavy fields from list/tree endpoints, added per-item detail RPCs that detect and reject stale catalog versions, cutting payload size and giving the UI a precise signal to reload instead of silently serving outdated data.
- Built an **external-system ingestion API** (for an automated test-runner client) with idempotent upsert semantics and solved a cross-cutting auth/serving problem — getting a relatively-linked two-file HTML report (with an iframe-embedded child document) to render correctly through a JSON API gateway by serving it via path-scoped cookie auth and same-origin sibling routes.
- Implemented **multi-tenant access control**: per-account catalog restrictions, many-to-many site/tester assignment, and mid-session re-validation (not just login-time) of role, site membership, and account-active status — enforced consistently across REST, gRPC interceptor, and periodic poll layers.
- Drove **performance optimization across the stack**: eliminated N+1 queries via JOIN consolidation, added server-side pagination/sort/filter to list endpoints, moved id→name resolution server-side to delete client-side lookup-map code, and fixed frontend rendering bottlenecks (chunked/batched DOM mounting, deferred heavy renders, memoized derived state) on views handling 1000+ row datasets.
- Diagnosed and root-caused subtle distributed-systems bugs end-to-end across client and server — e.g., traced a silent duplicate-record bug to a single unguarded edge case (empty device identifier bypassing every safety check) by correlating commits across two services; fixed a WebSocket false-disconnect bug caused by a too-narrow liveness check.

## Supporting talking points (for interviews)

**Concurrency design (best story):** The system needed to let multiple testers work the same test session at once without clobbering each other's edits. I modeled the operations into two classes — structural changes (create test object, change selected test items, finalize/generate report) and field-level result fills — and gave each a different locking strategy: structural ops take an exclusive advisory lock and bump an explicit revision counter via a single atomic `UPDATE ... WHERE revision = $2` statement (so staleness is detected with zero race window), while concurrent fills take a shared lock and merge per-field against a baseline so two testers editing different fields of the same row never lose data. I wrote out the full pairwise interaction matrix (create × edit × fill × finalize) before implementing, specifically to reason about every race condition up front rather than patch them as they were reported.

**Event-driven architecture:** Rather than have clients poll, every successful mutation publishes one `ActiveEvent` (actor + structured diff) that is simultaneously: (1) broadcast live over WebSocket to refresh other testers' UIs, (2) written to an append-only audit table in the same transaction as the mutation, and (3) consumed by the originating client itself to confirm its own write succeeded — one event, three consumers, no duplicated logic. The firmware-event pipeline applies the same pattern at the database layer: a Postgres trigger fires `pg_notify`, a dedicated LISTEN connection fans out to N concurrent gRPC stream subscribers filtered server-side by client-specified criteria.

**Cross-team schema ownership:** When a backend data-model changed (products/firmwares moving to an external system's IDs), I wrote up the migration as a cross-repo contract — documenting exactly which fields crossed which layer (Firebase → sync service → Postgres → protobuf → gateway → two UIs) — because no single repo's diff told the whole story and a future reader needed the map.

---

**Why this maps to AI engineering:** Multi-agent and agentic systems hit the identical class of problems this project solved — multiple writers (agents/tools) mutating shared state need conflict detection and merge strategies, not last-write-wins; agent action traces need the same append-only, broadcastable event model used here for live "who changed what"; and tool/function schemas need the same kind of versioned, codegen-enforced contract discipline as the protobuf pipeline above. The skill transferring directly is the architecture, not the domain.
